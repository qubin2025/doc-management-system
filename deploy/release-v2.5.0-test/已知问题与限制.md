# 全过程工程咨询管理系统 — 已知问题与限制清单（v2.5.0-test）

> 本清单记录测试版本上线时已知的问题、限制与规避方案。
> 优先级：P0 = 必须处理（安全/数据）；P1 = 重要；P2 = 优化项。

---

## P0 安全类（上线前必须处理）

### 1. 管理员账号为弱密码

- **现象**：`admin` 与 `管理员` 账号密码均为 `admin123`
- **风险**：任意可访问系统者可登录管理员
- **处理**：上线前执行
  ```bash
  cd backend
  node -e "const bcrypt=require('bcrypt');const db=require('better-sqlite3')('./data/planning.db');db.prepare('UPDATE users SET password_hash=? WHERE username IN (?,?)').run(bcrypt.hashSync('你的强密码',10),'admin','管理员');"
  ```
- **验证**：用新密码登录，旧密码登录失败

### 2. 前端 .env 含真实 API Key

- **现象**：项目根 `.env` 内含 `VITE_DEEPSEEK_API_KEY`、`VITE_ZHIPU_API_KEY`、`VITE_QWEN_API_KEY` 真实密钥
- **风险**：若将整个项目文件夹分发（未排除 .env），密钥随之泄露；VITE_ 前缀变量若被代码引用会打进前端构建产物
- **现状**：`.env` 已被 .gitignore 排除，**未提交到 GitHub**；前端仅 DesktopDailyReport.tsx 通过 `window.__env` 运行时读取（未打包进 bundle）
- **处理**：
  1. 交付/拷贝项目时**严禁包含 .env**（安全交付清单已声明）
  2. 上线前清空前端 .env 中的真实 key，仅保留占位符
  3. 如担心历史泄露，去各平台控制台轮换 key
- **验证**：`git ls-files .env` 输出为空

### 3. docker-compose 默认弱配置

- **现象**：`docker-compose.yml` 中 `JWT_SECRET` 默认 `change-me-in-production`、`NEO4J_PASSWORD` 默认 `changeme123`
- **风险**：Docker 部署时若未注入环境变量，使用默认弱口令
- **处理**：Docker 部署前必须导出：
  ```bash
  export JWT_SECRET=$(openssl rand -hex 32)
  export NEO4J_PASSWORD=<强密码>
  docker compose -p docmgmt up -d
  ```

### 4. CORS 与 NODE_ENV

- **现象**：开发模式 CORS 为 `*`，`NODE_ENV=development`，`LOG_ENV_TAG=DEV`
- **处理**：生产/试运行部署时设置 `NODE_ENV=production`、`CORS_ORIGIN=实际域名`、`LOG_ENV_TAG=PROD`（后端 .env 修改后重启）

## P1 重要类

### 5. 测试套件 4 个文件失败

- **现状**：✅ **已修复（2026-10-21）**。21 个测试文件、150 个用例全部通过。
- **修复内容**：backend.test.ts 登录凭据改为环境变量可配置（`TEST_USERNAME`/`TEST_PASSWORD`）；KnowledgeBase/AgentConsole/Dashboard 多元素断言改用 `getAllByText`；Dashboard 断言文本同步实际组件文案
- **注意**：运行后端集成测试需设置 `TEST_PASSWORD=<当前管理员密码>`，否则登录用例失败

### 6. 版本号不一致

- **现状**：已统一为 **v2.5.0**（server.js /admin.js 版本常量已修正，2026-10-21 完成）
- **验证**：重启后端后 `curl http://localhost:3000/api/health` 返回 `version: 2.5.0`

### 7. 数据备份为空

- **现象**：`backend/backups/` 目录无有效备份文件
- **风险**：数据库（planning.db）与上传文件（backend/files）无备份，故障即丢失
- **处理**：上线前执行一次完整备份并验证恢复；建立每日备份任务（项目含 `deploy/deploy-cron.sh`、`deploy/crontab.txt` 可参考）

### 8. Python 微服务非托管进程

- **现象**：LightRAG(8000)、PaddleOCR(8001) 以裸 Python 进程运行，未纳入 Docker/PM2/systemd
- **风险**：机器重启后需手动拉起，忘记则系统部分功能不可用
- **处理**：测试期间参照《运维手册》启动；正式上线前应迁移到 Docker Compose（docker-compose.yml 已含 lightrag/paddleocr 服务）或 PM2

### 9. OCR 引擎懒加载

- **现象**：PaddleOCR 服务依赖 paddleocr/paddlepaddle 包为懒加载，当前未安装完整 OCR 包
- **影响**：扫描型 PDF/图片的文字识别可能不可用（文本型 PDF 不受影响）
- **处理**：需要扫描件识别时安装：
  ```bash
  pip install paddleocr paddlepaddle
  ```

## P2 优化类（测试期间迭代）

### 10. 后端启动探针 OFFLINE 误报

- **现象**：启动日志中 Neo4j/RAGFlow/LightRAG/PaddleOCR 探针报 `TypeError fetch failed` 但服务实际在线
- **原因**：Node 的 fetch 走了系统代理访问 localhost 失败
- **处理**：验证服务以 `/api/health`、`/api/stats` 为准；或后端探针改用 `127.0.0.1` + 禁代理

### 11. 大组件代码健康

- **现象**：21 个组件 >250 行（App.tsx 934 行、GuideChapter.tsx 697 行等）
- **影响**：维护成本高，但不影响功能
- **处理**：迭代拆分（已有 NEXT_PHASE_PLAN 计划）

### 12. 无端到端测试

- **现象**：无 Cypress/Playwright 流程测试
- **处理**：试运行稳定后补核心流程 E2E

### 13. 上传大小限制历史

- **说明**：早期 50MB 限制（base64 端点）仍在，但 **multipart 流式端点已实现，单文件上限 200MB**（支持 100MB+ CAD 图纸），ZIP 解析上限 50 文件。前端默认走 multipart。旧 base64 端点仅作兼容。

### 14. 测试账号残留

- **现象**：user1~user8、test3 等测试账号存在
- **处理**：测试阶段可保留；正式上线前删除
