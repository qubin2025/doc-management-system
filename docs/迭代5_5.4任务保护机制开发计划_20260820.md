## 二、新旧方案对比（基于豆包 thread xOK61W8Bm3LVBDLvm 建议）

### 2.1 失败退避

| 维度 | 原方案 | 豆包建议 | 采纳 |
|------|--------|---------|------|
| 退避间隔 | 1s/2s/4s | **30s/60s/120s** | ✅ |
| 实现机制 | 立即重置 pending | `next_run_at` 字段 + 拉取过滤 | ✅ |
| 表结构 | 不动 | 加 `next_run_at TEXT`（默认 NULL） | ✅ |

**理由**：嵌入服务过载恢复需时间，短退避会让雪崩持续；1s/2s/4s 只对瞬时抖动有用，对真实过载无效。

### 2.2 优雅退出

| 维度 | 原方案 | 豆包建议 | 采纳 |
|------|--------|---------|------|
| 等待对象 | 1 个当前任务 | **所有 in-flight 任务**（MAX_CONCURRENT=3 可能 3 个并发） | ✅ |
| 强制超时 | 无 | **15 秒强制退出**（嵌入 30s 超时，不能无限等） | ✅ |
| 超时处理 | — | 解锁本 worker 任务 → 重置 pending → state=stopped | ✅ |

**理由**：当前任务可能卡在嵌入调用上（30s 超时），无限等会卡死进程；直接退回会导致状态不一致。

### 2.3 内存上限

| 维度 | 原方案 | 豆包建议 | 采纳 |
|------|--------|---------|------|
| 阈值 | 100 chunks 或 500KB | **总文本量 > 2MB**（去 chunk 数量限制） | ✅ |
| 触发动作 | 跳过 + 告警 | 跳过 + 告警（**预留分批处理接口**） | ✅ |
| 检测时机 | 分块后 | **解析阶段就预检**（防 OOM） | ✅ |

**理由**：100 chunks 阈值太严，工程规范/长合同很容易超；大文档才是最该入库的；解析大 PDF 本身就可能 OOM。

## 三、具体修改点清单

### 3.1 backend/db.js

```sql
-- migration: 5.4 失败退避
ALTER TABLE kb_sync_queue ADD COLUMN next_run_at TEXT;
CREATE INDEX IF NOT EXISTS idx_kb_queue_next_run ON kb_sync_queue(status, next_run_at);
```

兼容性：旧数据 next_run_at = NULL，拉取条件用 `IS NULL OR <= now` 兼容。

### 3.2 backend/services/kbWorker.js

**constructor 新增字段**：
```javascript
this.inFlightTasks = new Set();    // 当前正在处理的任务 id 集合
this.shutdownTimeoutMs = 15000;    // 优雅退出强制超时
this.maxTextBytes = 2 * 1024 * 1024;  // 2MB 文本上限
```

**_pollOnce 拉取条件**：
```sql
SELECT * FROM kb_sync_queue
WHERE status='pending'
  AND (next_run_at IS NULL OR next_run_at <= datetime('now'))
ORDER BY priority DESC, created_at ASC LIMIT ?
```

**_markRetry 退避计算**：
```javascript
const backoffSeconds = [30, 60, 120][Math.min(newRetry - 1, 2)];
// UPDATE ... SET next_run_at=datetime('now', '+N seconds')
```

**_processOne 维护 inFlightTasks**：
```javascript
this.inFlightTasks.add(task.id);
try { ... } finally { this.inFlightTasks.delete(task.id); }
```

**stop() 优雅退出**：
```javascript
stop() {
  this.state = STOPPING;
  const t0 = Date.now();
  const checkInterval = setInterval(() => {
    if (this.inFlightTasks.size === 0 || Date.now() - t0 > this.shutdownTimeoutMs) {
      clearInterval(checkInterval);
      if (this.inFlightTasks.size > 0) {
        // 超时强制解锁
        db.prepare(`UPDATE kb_sync_queue SET status='pending', locked_by=NULL, locked_at=NULL WHERE locked_by=?`)
          .run(this.workerId);
      }
      this.state = STOPPED;
    }
  }, 200);
}
```

**_processTask 文本预检**：
```javascript
const totalBytes = segments.reduce((sum, s) => sum + Buffer.byteLength(s.text, 'utf8'), 0);
if (totalBytes > this.maxTextBytes) {
  logger.warn(`Task ${task.id} 文本 ${totalBytes} bytes 超 2MB 上限，跳过（预留分批处理）`);
  return;  // 跳过，但任务标记为 done（不重试）
}
```

### 3.3 backend/services/docParser.js

**parseDocument 入口加文件大小预检**：

const MAX_FILE_SIZE = 10 * 1024 * 1024;  // 10MB
if (buffer.length > MAX_FILE_SIZE) {

## 四、验证方案

### 4.1 单元场景测试

| 场景 | 预期 |
|------|------|
| 任务失败 1 次 | next_run_at = now+30s，30s 内不被领取 |
| 任务失败 2 次 | next_run_at = now+60s |
| 任务失败 3 次 | status=failed（终态） |
| Worker stop() 时 0 个 in-flight | 立即退出 |
| Worker stop() 时 3 个 in-flight | 等所有完成或 15s 超时 |
| 文本 >2MB | 跳过+告警，任务 done |
| 文件 >10MB | parseDocument 抛错 |

复用 5.3h 的 e2e 测试，确认正常路径不受影响。

## 五、风险与回退

| 风险 | 应对 |
|------|------|
| migration 失败 | ALTER TABLE 幂等性差，用 try/catch 包裹 |
| 退避过长导致任务积压 | 监控 pending 队列长度，超 100 告警 |
| inFlightTasks 内存泄漏 | _processOne 用 try/finally 确保 delete |
| stop() 死循环 | checkInterval 有 15s 超时兜底 |
