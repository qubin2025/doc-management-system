一、屎山形成与治理全过程

1.1 屎山形成期（v4.1 → v4.4）

2026年7月14日至21日，项目从v4.1快速迭代到v4.4。期间新增12个组件、6个数据模块、8个API端点，代码量从~26,000行膨胀到~34,000行。 核心问题在于：每次新增功能都直接往 App.tsx 追加 if-else 路由，导致该文件从~1100行增长到1373行。 同时，多个后端路由文件超过500行门禁（kg.js 579行、ai.js 536行），功能混杂在一个文件中。

1.2 屎山爆发事件（2026-07-24）

⚠ DesktopDailyReport.tsx 文件损毁事件

为接入 PromptConfigDialog 组件（仅需3行代码），因反复使用 sed 和 node -e 进行碎片化行内修改，导致文件 JSX 结构损毁：丢失KV组件、产生重复闭合标签、函数作用域错乱。累计消耗2+小时无效排错。 根本原因：自动化脚本不理解JSX层级结构，碎片化补丁逐步腐化文件结构。

1.3 屎山识别诊断（2026-07-25）

综合评估代码健康度得分 5.6/10，识别出四大红线文件：

文件行数门禁超限比核心问题
App.tsx1,373250+449%39个视图 if-else 链，每次加功能必膨胀
GuideChapter.tsx1,341250+436%~350行SVG遗留死代码
kg.js579350+65%基础CRUD与GraphRAG混在一起
ai.js536350+53%7模型代理+用量统计+管理端点混杂

1.4 屎山治理成果（v5.1 还债止血）

文件治理前治理后减幅方案
App.tsx1,373行934行-32% 抽出 HomePage (219行) + StandardSelectPage (70行) 两个独立组件

关键设计决策： ai.js 的核心链（chat→GraphRAG→限流→模型降级）形成强耦合调用链，硬拆会破坏内聚性，因此仅抽离与chat无关的管理端点。这与kg.js的拆分策略不同（kg.js的GraphRAG端点完全独立，可直接抽离）。

二、防屎山开发准则 v2.0

2.1 硬门禁（强制执行）

#规则违规后果
1新增文件 ≤ 250行（从300行收紧）不予合入
2禁止新增 any 类型不予合入
3跨3层传参必须用 Context（禁止 prop drilling）不予合入
4仅用 Write/Edit 修改 TSX，禁止 sed/node-e立即回退
5新组件必须有测试文件不予合入
6禁止向 App.tsx 追加 if-else 路由（新增🔥）立即回退
7同文件修改 >3次即整体重写（新增🔥）停止修补

2.2 页面固定结构规范

导入区 → 类型定义区 → 状态定义区 → 业务方法区 → 纯JSX渲染区 → 导出区

不允许打乱层级穿插代码。新页面严格遵循，老页面重构时统一规整。

2.3 迭代卡点止损机制

if (TSC 错误数 > 3)     → 停止修补 → Write 完整重建
if (同一文件已修改 >3次) → 停止修补 → Write 完整重建
if (sed/node-e 修改后编译失败) → 立即回退 → 手动开发
if (JSX 结构解析异常)   → 立即止损 → 切换手动标准化开发
if (老旧破损文件)        → 永久禁用自动化注入 → 仅手动规范开发

2.4 新增功能审批清单

✓ 是否可复用现有组件/模块？
✓ 是否必须新建文件？（≤250行）
✓ 是否避免了向 App.tsx 追加路由？
✓ 是否避免了 prop drilling >3层？
✓ 是否有对应测试文件？
✓ 是否更新了 CLAUDE.md 和操作说明书？

三、开发过程经验教训

3.1 技术教训

教训一：sed/node-e 是 TSX 文件的毒药

场景： DesktopDailyReport.tsx 接入 PromptConfigDialog，仅需3行代码。
错误做法： 用 sed 行内替换 + node -e 注入代码，多次碎片化修改。
结果： Bash转义与JS语法叠加错误率极高，2+小时无效排错。
正确做法： 直接使用 Write 工具完整重写文件，确保结构规整。

教训二：内联 JSX 是路由膨胀的根源

场景： App.tsx 的 homepage 视图以427行内联 JSX 嵌入 if-else 链中。
后果： 每次新增功能卡片，直接往 App.tsx 追加代码。
解决方案： 抽出为独立 HomePage.tsx 组件，用数据驱动的卡片配置替代硬编码。

教训三：bash/curl 传输中文数据需验证编码

场景： 通过 bash curl 向 Neo4j 写入含中文的测试数据。
问题： shell 编码问题导致中文字符变为 \uFFFD 替换字符。
解决方案： 用 Node.js 脚本直接调用 neo4j-driver 写入，避免 shell 编码层。

教训四：Git checkout 是双刃剑

场景： 运行 git checkout -- src/ 回退文件，丢失了v4.4全部新增代码。
后果： 62个TSC错误，需手动恢复 api.ts、mobileApi.ts 等文件的所有类型和函数。
教训： checkout 前确认改动已提交；使用 git stash 代替 checkout 撤销。

3.2 架构教训

教训五：单例模式是状态管理的瓶颈

项目中 engineeringAgent、skillRegistry、mcpRegistry、orchestrator 均为全局单例。 这在单页面场景下工作正常，但缺少 Context 导致30+组件通过 prop drilling 共享 currentProject。 长期方案： 引入 React Context 统一跨组件状态管理。

教训六：字符串视图路由不可类型安全

39个视图通过 setView('string') 切换，无编译时检查。 拼写错误（如 'dashboard' vs 'dashbord'）直到运行时才暴露。 长期方案： 路由配置对象 + 联合类型约束，编译时捕获错误。

教训七：拆分策略需因文件制宜

kg.js 的 GraphRAG 端点完全独立 → 可直接抽离文件（579→125行）。
ai.js 的 chat→GraphRAG→限流→降级形成强耦合链 → 仅抽离管理端点（536→451行）。
原则： 不为了"干净"而破坏内聚性；优先抽离与核心调用链无关的部分。

3.3 流程教训

教训八：文档与实际规模脱节是隐患

CLAUDE.md 报告38组件/22模块，实际为62组件/34模块。文档与代码的偏差导致门禁规则失效。 解决： 每个迭代结束强制更新 CLAUDE.md 统计数据。

教训九：功能膨胀比代码膨胀更危险

v4.4开发中需求从"手机端日报"扩展到8个领域30+需求项，导致一次性新增~6500行代码。 原则： 每个迭代聚焦3-5个核心需求，其余进入 backlog。
