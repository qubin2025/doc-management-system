零、系统设计哲学与核心理念

0.1 根本认知：建设工程项目是单一的、一次性的、不可复制的

本系统的设计出发点是承认一个被传统工程管理软件长期忽视的事实：每一个建设项目都是独一无二的。 它的场地条件、气候环境、团队构成、分包组织、材料供应、甲方要求……所有这些因素组合在一起，构成了一个不可复制的整体。试图用一个"标准化模板"去套用所有项目，就像用一把刻度尺去丈量海洋——你能得到数字，但永远无法理解海洋。

0.2 传统数据方法为何失败

传统工程管理软件遵循"先有指标体系，再采集数据"的路径。它们预设了"成本偏差率"、"进度偏差率"、"质量合格率"等有限指标，然后要求项目去适应这些指标。这种做法有三个致命缺陷：

  1. 信息损失：项目复杂性的99%被丢弃，只保留了几个百分比数字
  2. 无法描述独特性：每个项目的独特之处（为什么这个分包商效率高？为什么那天下雨导致延误？）在标准化过程中消失
  3. 对标陷阱：与"类似项目"的比较看似科学，实则忽略了项目的本质差异，给出的"建议"往往不痛不痒

0.3 本系统的数据哲学

核心原则：全量数据收集 > 标准化指标提取

我们深受《大数据时代》的启发，采纳其三个核心洞见：① 拥抱全量数据而非抽样；② 接受数据的混杂性而非追求精确；③ 关注相关关系而非只追问因果。

在这个时代，AI大模型提供了近乎无限的全方位向量化数据分析能力。我们不再需要人为预设"重要的指标"——我们只需完整地收集项目的全部数据，然后让AI去发现数据之间的关系、趋势和模式。这意味着：

  • 日报的每一个字段都被保存，不是摘要
  • 安全检查的每一次记录都被关联，不是统计
  • 每一个协调问题的来龙去脉都被追溯，不是打勾
  • 每一台机械、每一批材料、每一个人员变化都被记录，不是忽略

数据不为归档而生，数据为理解而生。

0.4 六个工程设计原则

#原则说明
1全量收存不预设重要性筛选，收集项目全生命周期产生的全部数据。日报8板块全字段入库，施工照片原图保存，原始DOCX双份存档。
2拒绝裁剪不为了"标准化"而丢弃任何数据。每个项目的独特细节都是其DNA的组成部分。结构化数据库保留完整JSON字段，原始文档保留一字不改。
3AI驱动关联利用AI大模型的向量化分析能力，从全量数据中自动发现关系、趋势和模式。DeepSeek日报解析、Recharts趋势图表、知识图谱25类节点全要素关联。
4项目即样本每个完成的项目都是一个完整的、可供后续项目参考的真实样本。项目经验库自动提取模式，跨项目对比分析基于完整数据而非有限指标。
5以PMBOK为纲以《项目管理指南》的准则和行动要素为骨架，系统化地组织和归纳数据。5大过程组×10大知识领域为框架，确保数据的系统性。
6可见即可信不满足于报表数字，追求数据的完整性和可视化，让项目的全貌一望便知。3D知识图谱、Dashboard实时图表、日报全8板块展开视图。

0.5 系统的终极目标

为全过程工程咨询、项目管理、工程管理提供活生生的样本和可借鉴模型。

它们是完整的、丰满的，一望便知的——无论是美的还是丑陋的。通过本系统，可见的是以此作为下一个项目的指路者。

数据不为归档而生，数据为下一个项目而生。

一、有效开发提示词方法论总结

1.1 十大高效交互模式

1. "请梳理、分析该项目开发内容和进度后，帮我分析这个全过程工程咨询项目已完成的开发内容的实际情况是否与目标一致"
模式：全局审视 → 差距分析。 这是整个开发过程最关键的prompt——它促使了从"盲目开发"到"目标对齐"的转变。不是问"下一步做什么"，而是先问"现在的位置和目标差多远"。
2. "请根据目前梳理的开发进度及后续需开发内容形成下一步开发计划，确保项目开发目标不打折扣的实现，可落地部署"
模式：目标约束 → 可落地计划。 不满足于方案本身，而是追问可执行、可验证的落地路径。"可落地部署"四个字将讨论从理论拉回实践。
3. "这个降级链是什么意思？" / "目前正在开发什么？还有哪些需要完善？"
模式：概念追问 → 深度理解。 对专业术语不满足于表面理解，追问本质。这种追问成本极低但收获极大——它让开发者确认用户真正理解了系统设计，避免后续误解。
4. "检查所有配色方案，在白色方案下，模块裁剪引擎未选中项的框内颜色太深，导致字体可视度差，不易识别，请检查所有类似情况"
模式：点状发现 → 全局排查。 不满足于修复一个bug，而是要求系统性地检查同类问题。这是工程思维的核心——"发现一个，修复一类"。
5. "请根据项目开发目标及建议开发内容绘制系统最终开发系统图，明晰系统开发构架"
模式：可视化需求 → 架构确认。 文字讨论容易遗漏和模糊，要求用图表达迫使系统化和完整化。架构图一旦画出，漏洞一目了然。
6. "技能面板卡片中各项技能使用体验不佳...该卡片内对各项技能应着重展示AI应用能力，指出技能所在位置"
模式：体验驱动 → 重新设计。 不是要求"加功能"，而是指出"现有设计不符合使用场景"。这种从用户角度出发的反馈是最有价值的输入。
7. "请阅读上传文档，判断文档分析是否适用于系统AI智能体开发，结合本系统开发目标思考判断后，在保持目标不变的情况下，制定适用的方案"
模式：外部输入 → 自主判断 → 适配实施。 不是盲目采纳外部方案，而是要求AI先分析、再判断、后适配。保留决策权的同时利用外部智慧。
8. "请以项目管理专家的视角审视该项目目前开发进度及后续落地"
模式：角色切换 → 专业视角。 要求AI以特定角色身份审视问题，获取不同维度的洞察。项目管理专家的视角关注的是"能否交付"而非"代码好不好"。
9. "先回答核心问题：是否部署前需要逐个解决四个瓶颈？"
模式：优先级排序 → 资源聚焦。 面对多个问题时，不是逐一解决，而是先判断哪些是阻塞性的、哪些可以延后。这是管理者思维的核心。
10. "请根据开发报告梳理开发内容修改提升、新增开发模块功能与价值，整个项目体系的提升"
模式：阶段性复盘 → 价值量化。 每个阶段结束要求全面复盘，将技术工作转化为可量化的业务价值。这是面向领导汇报的必备能力。
11. "v4.3+v4.4的功能验证是否与v4.5的开发完成与否有联系？如果完成4.5的开发对之前版本的验证无影响，就先继续开发"
模式：阶段性依赖判断 → 并行决策。 多版本迭代中，先判断各阶段之间的耦合关系——是独立并行的还是顺序依赖的。独立则先完成全部开发再统一验证，避免"开发→验证→开发→验证"的串行低效。判断方法：列出两个阶段各自改动的文件/模块/接口，逐项比对，无交集即独立。这是工程管理中的关键路径识别在AI辅助开发中的直接应用。

1.2 交互模式总结

模式类型关键特征产生效果
全局审视型要求宏观盘点、差距分析、完成度评估避免方向偏离，确保目标对齐
概念追问型追问术语含义、工作原理、边界条件消除认知偏差，确认理解一致
系统性排查型"所有类似情况"、"全部检查"用工程方法解决工程问题
可视化确认型要求图表、架构图、流程图复杂概念一次对齐
体验驱动型从用户视角指出不合理之处功能→好用→顺手
目标约束型"确保目标不打折扣"、"可落地"方案不过于理想化
阶段复盘型要求总结、量化、对比积累知识资产，可追溯
依赖判断型先判断阶段间耦合再决定串行/并行关键路径识别，避免伪依赖导致低效

三、结合PMBOK、全过程工程咨询与AI前沿的下一步方向

3.1 三个需要补强的方向（基于差距分析）

方向一：目标→成果→价值度量链（PMBOK第7版核心）

当前系统实现了"目标→工作项"的分解，但缺少从"工作项完成"到"成果交付"到"价值实现"的完整度量链。PMBOK第7版强调的8大绩效域中，"交付"和"度量"两个域与第6版的传统知识领域有本质区别——它关注的是成果是否产生了价值，而非仅仅"是否按计划完成"。

建议：在目标管理中增加"价值度量"维度——每个目标关联一个可量化的业务价值指标（成本节约额、工期缩短天数、质量提升百分比），Agent定期自动评估价值实现度。

方向二：知识飞轮闭环（AI持续学习）

当前系统的知识反馈闭环尚未完整建立。AI生成审查报告后，用户的👍/👎评分存储在localStorage，但未反馈到AI模型的能力改进中。积累的项目数据（工作项完成模式、审查结果分布、风险实际发生情况）是训练行业专属AI的宝贵语料。

建议：①建立AI输出质量评分体系（用户评分+专家抽查+自动化校验）；②积累足够数据后微调开源LLM（Qwen2.5-14B）形成行业专属模型；③建立"项目经验库"——从历史项目提取成功模式和失败教训，Agent在新项目中主动提示。

方向三：全过程咨询的移动化与现场化（行业刚需）

全过程工程咨询的核心场景是现场——工地踏勘、隐蔽工程验收、监理旁站、安全巡检。当前系统是PC中心化设计，手机端配套应用虽已规划但未完成开发。这是工程咨询区别于其他项目管理领域的关键差异化需求。

建议：优先完成手机端水印相机+现场问题上报+离线任务管理（已在方案中规划），然后扩展到语音输入、AR测量、BIM模型查看。手机端不是"PC端的缩小版"，而是独立的现场工作平台。

11.1 AI 模型配置修复

问题：大模型配置中心全部测试按钮无反应，所有模型显示离线

根因说明
dotenv 路径错位server.js 使用 import 'dotenv/config' 从 CWD 加载 .env，但服务器从项目根目录启动，读到的 .env 仅含 VITE_* 前端变量，缺少 DEEPSEEK_API_KEY 等后端变量。实际 API Key 存放在 backend/.env
ES模块提升ai.js 在模块初始化时读取 process.env.DEEPSEEK_API_KEY，早于 dotenv.config() 执行，导致 MODELS 配置的 key 均为 undefined

修复：

  • server.js: 改用显式路径 dotenv.config({ path: resolve(__dirname, '.env') }) 确保加载 backend/.env
  • ai.js: MODELS 从 const 改为 function getModels() 延迟求值，确保 process.env 已填充
  • 中间件 auth.js: requireAuth SQL 查询补充 display_name 字段，getMe() 返回 displayName

结果 DeepSeek/V4/R1 + 通义千问 + 智谱GLM 共5个云端模型全部在线

13.3 各方案详析

方案A：SQLite + 专用硬盘（推荐）

架构：daily_reports 表（结构化数据源）→ Recharts 图表 + /daily-uploads/ 目录（原始文档归档）→ 审计追溯

  • 零新增依赖，即刻可用（系统已有 daily_reports 表 + daily-uploads/ 目录）
  • 完美满足「数据主权」最高原则
  • 匹配单项目几十MB数据量级（日均~5KB，10年≈18MB）
  • 90%已就绪，仅需补齐子表拆分

方案B：PostgreSQL + MinIO（企业级）

适合团队>10人、多项目并发、需多端同步场景。当前项目为单机部署，过度设计。新增Docker运维负担，违反「少即是多」原则。

方案C：MongoDB + GridFS（NoSQL）

文档型数据库适合非结构化数据，但 Recharts 需要结构化 SQL 查询。引入新的技术栈增加运维成本，聚合管道学习曲线陡峭。

方案D：云SaaS（简道云/明道云）

直接违反「数据主权」最高原则，数据存储在第三方服务器。不可接受。

13.4 最终推荐：方案A

决策因素说明

零新增成本无需安装新软件、购买服务、学习新工具
完全离线数据完全在本地，满足涉密/私有化交付要求

结论：采用「SQLite结构化数据库（看板数据分析）+ 项目专用硬盘原始文档归档（全量兜底）」双存储架构。

十四、代码修改红线与经验教训（2026-07-24）

14.1 事件背景

2026年7月24日迭代开发中，DesktopDailyReport.tsx 因反复使用 sed -i、node -e 等 Shell 脚本进行碎片化行内修改，导致文件 JSX 结构彻底损毁——KV 组件丢失、重复闭合标签、函数作用域错乱，累计消耗 2+ 小时无效排错。PromptConfigDialog 组件本身（240行完整代码）无需任何修改，但在接入时因目标文件损毁，自动化注入全部失败。

核心教训：不是 AI 能力不足，而是用错了工具。sed 不理解 JSX 层级结构，node -e 在 bash 转义层与 JS 语法层叠加后出错率极高。正确的做法是一开始就用 Write 工具完整重写文件。

14.2 三大红线（绝对禁止）

红线说明根因
🚫 禁止 sed 修改 TSX/JSX不允许用 sed -i 对 .tsx 文件做行内替换sed 不理解 JSX 标签嵌套结构，容易破坏闭合、作用域
🚫 禁止 node -e 行内注入不允许用 inline Node.js 脚本向组件文件注入代码Bash 转义 + JavaScript 语法叠加，出错率 > 80%
🚫 禁止碎片化补丁不允许对同一文件多次零散修改多次碎片补丁导致结构腐化，形成「屎山」

14.3 替代方案（必须遵守）

场景正确做法工具
修改 >5 行完整重写文件，确保结构规整Write 工具
修改 1-3 行精确匹配替换，确保 old_string 唯一Edit 工具
新增功能创建独立组件，避免侵入已有复杂页面新建 .tsx 文件
TSC 错误 >3 个立即停止修补，Write 完整重建止损回退
同一文件已修改 >3 次停止修补，Write 完整重建防止结构腐化
