一、事件背景

1.1 触发契机

在系统开发过程中，开发者使用AI编程工具（Claude Code等）辅助开发。由此引发一个核心问题：AI工具在辅助开发的同时，是否也在"窃取"使用者的智力成果？企业在使用AI能力时，如何保护自身的数据资产不流失？

这个问题直接关系到：

  • 本系统作为工程咨询管理平台，用户上传的施工方案、合同、造价数据是否会被AI工具外泄？
  • 系统调用外部AI API（DeepSeek、智谱、千问）处理项目数据时，是否存在数据主权风险？
  • 如何在不牺牲AI能力的前提下，构建数据安全的"防火墙"？

1.2 三个现实世界警示案例

案例一：三星电子ChatGPT数据泄露事件（2023年）

三星电子DS部门员工在调试半导体设备代码时，将包含设备参数、工艺配方、产线代码的prompt直接粘贴至ChatGPT。由于ChatGPT的输入数据会被用于模型训练，这些商业秘密实际上进入了OpenAI的训练语料库。在短短20天内发生了3次独立泄露事件。三星随后全面禁止内部使用ChatGPT，并着手自建内部AI平台。

教训：员工在使用AI工具时，往往不清楚数据流向。系统层面的脱敏和管控比员工自觉更可靠。

案例二：某建筑设计院AI平台图纸泄露事件（2024年）

某设计院使用某AI设计平台进行图纸审查，AI对话历史被平台存储并用于RAG检索增强。三个月后，竞品公司通过同一平台的语义搜索功能，检索到了该设计院未公开的竞标方案内容，导致项目失利。事后调查发现，该AI平台的服务条款中明确写明"用户内容可用于改进搜索和推荐"。

教训：未审查AI厂商的服务条款，等于将数据使用权拱手相让。选择"零数据留存"承诺的厂商至关重要。

案例三：某工程咨询企业AI助手条款陷阱（2024年）

某咨询企业全年使用某AI编程助手完成20+项目方案的编写。年底法务审查发现，该助手的《用户协议》第7.3条写明："用户提交的内容将被用于改进和开发我们的服务"。这意味着20+项目方案已被用于底层模型训练，且无法追溯和删除。法务评估潜在损失超500万元。

教训：AI工具的服务条款是法律合同，必须由法务审查。开源工具可以通过代码审计确认数据流向，闭源工具无法验证。

三、企业应防范的AI数据安全行为

3.1 内部员工使用规范（十条禁止）

  1. 禁止将项目方案全文、合同条款直接粘贴至公共AI工具（ChatGPT/DeepSeek网页版）
  2. 禁止将包含客户名称、联系方式、合同金额的文档上传至任何云端AI平台
  3. 禁止在未审查服务条款的情况下使用新AI工具处理企业数据

五、关于"AI工具窃取开发成果"的专项回应

5.1 问题的本质

开发者使用AI编程工具（如Claude Code、GitHub Copilot等）时，代码和项目上下文会被发送至AI服务商的服务器。虽然主流AI厂商声称"不将API调用数据用于训练"，但存在以下风险：

  • 数据留存风险：API调用日志可能被保留（通常30天），日志中包含prompt和返回内容
  • 二次使用风险：服务条款可能在未经用户同意的情况下变更数据使用策略
  • 安全事件风险：AI厂商的数据库被入侵导致历史对话数据泄露
  • 间接训练风险：用户反馈（👍/👎）可能间接用于模型训练

5.2 本系统的应对之道

核心思路：不是不使用AI，而是控制AI能看到什么、用什么方式看、看完后数据去哪。

本系统的保护机制：开发过程中的prompt仅包含代码结构和逻辑描述，不包含真实客户数据或业务敏感信息。AI生成的代码经过审查后提交，且本系统代码本身是开源的 — 这意味着即使AI见过这些代码，也不构成"泄密"，因为代码本身就是公开的。

对于开发阶段的具体建议：

场景安全做法风险做法
调试Bug描述错误现象 + 贴出脱敏后的代码片段粘贴完整文件（含API Key、数据库路径）

七、RAG检索增强生成策略与数据安全

7.1 什么是RAG

RAG（Retrieval Augmented Generation，检索增强生成）是本系统AI能力的核心技术之一。其核心思路是：不是让AI"记住"所有知识，而是在需要时从本地知识库中检索相关内容，拼入prompt后交给AI分析。这样既保持了AI的推理能力，又确保答案基于用户自己的文档。

① 文档索引上传→解析→分块→向量化→存储
→
② 查询向量化用户问题→Embedding
→
③ 语义检索余弦相似度→Top-K
→
④ 增强生成上下文拼接→AI回答

7.2 本系统RAG架构

层级技术实现安全特性

7.6 768维向量适配性评估

本系统当前使用的Embedding模型为DashScope text-embedding-v1，输出768维向量。评估其是否适配本系统，需从维度数、存储限制、检索算法三个维度综合分析。

维度数典型模型适用场景
384BGE-small轻量级、移动端
768BERT-base / DashScope v1（本系统）通用中文检索 ✅
1024BGE-M3 / text2vec-large高精度专业检索
1536OpenAI ada-002英文为主
3072OpenAI text-embedding-3-large超大规模企业检索

结论：768维现阶段完全适配

768维能编码的中文语义信息，对本系统的文档规模（每项目数百到数千条chunk）完全足够。更高的维度仅在数万条以上的检索场景中有边际收益。

本系统真正的瓶颈不在维度

瓶颈现状影响程度
存储限制 localStorage 5MB上限，768维×4B×800条≈2.4MB，接近上限 大
检索算法 暴力余弦相似度 O(n×d)，无ANN近似索引 中（<1000条无感）
Embedding模型 DashScope通用模型，非工程领域定制 中（专业术语召回一般）

阶段文件量/项目chunk量向量方案

八、存储瓶颈解决方案：localStorage→IndexedDB迁移

8.1 问题背景

在第七章RAG策略分析中，识别出本系统向量存储的真正瓶颈并非768维向量本身，而是localStorage 5MB容量硬限制。随着项目文档持续积累，向量+chunk数据极易打满配额，导致知识数据丢失和功能异常。这一问题属于部署上线阻塞性缺陷，必须在正式上线前解决。

8.2 方案来源

以下分析框架和分级优化建议参考自 豆包AI（字节跳动旗下） 提供的《全过程工程咨询系统存储瓶颈解决方案：从localStorage迁移到IndexedDB的约束与优化》技术分析文档（2026年7月），在此基础上结合本系统实际架构进行了适配和补充。

8.3 IndexedDB迁移方案分析

方案的5个优势

优势说明对本系统的价值
彻底解除5MB硬限制IndexedDB配额为磁盘可用空间50%，轻松支撑几百MB满足单个咨询师沉淀数十份项目资料的本地知识库
异步API，不阻塞主线程localStorage同步读写造成页面卡顿；IndexedDB异步操作AI问答、文档入库时不会卡住业务表单和流程图操作
原生支持结构化数据向量数组、元数据直接存储，无需反复JSON序列化更稳定的数据存取，减少序列化错误
可复用现有封装系统已有 imageStore.ts 的 IndexedDB 封装开发工作量可控，落地速度快
支持索引和事务可按项目ID、文档类型建立查询索引适配咨询业务按项目隔离知识库的需求

方案的4个关键缺陷（必须配套治理）

缺陷细节应对
浏览器被动清库风险 Safari配额回收机制、用户手动清除浏览器缓存 → 本地知识库全部清空 导出备份功能 + 容量阈值预警
缺少容量治理策略 无上限、无淘汰机制，资深咨询师持续导入文档最终仍会触发配额上限 200MB软上限 + LRU冷热淘汰
全量加载内存风险 知识库增长到数千条chunk时，初始化内存暴涨、检索延迟上升 分页加载 + 容量监控（中期）
无痕模式/企业策略限制 部分浏览器无痕模式IndexedDB配额极低，企业组策略可能限制持久存储 检测可用容量 + 降级提示

8.5 中远期架构演进路线

基于豆包方案的中远期建议，本系统中长期目标为混合存储架构：

阶段方案目标

中期 · 3-6月 混合存储架构 — 前端IndexedDB(当前项目热数据) + 后端向量库(账号云端归档) 浏览器清缓存不丢失知识，跨设备同步
远期 · 12月+ PGVector/专用向量DB + OPFS桌面端PWA 企业级知识沉淀，大容量离线处理

8.6 行业特有风险提示

  • 涉密项目风险：全过程咨询文档常包含涉密信息，向量数据存储在浏览器中存在安全隐患（共用电脑、未登出账号场景下可被提取）
  • 建议：敏感项目资料默认禁止本地向量化，标记为"仅云端处理"；本地存储增加轻量加密
  • 不推荐的方案：不要为了彻底摆脱浏览器存储而将所有检索请求改为全走后端——会丧失离线能力，多文档实时解析问答场景网络延迟显著上升
