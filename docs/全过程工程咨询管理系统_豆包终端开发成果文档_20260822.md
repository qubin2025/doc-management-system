## 二、大文件上传改造（ABCD 四方案合一）

### 2.1 背景与问题

原系统存在多层上传限制叠加：
- Nginx：`client_max_body_size 100M`
- Express JSON body：生产 `10mb` / 开发 `100mb`
- 业务层：`MAX_FILE_MB = 50`
- docParser 解析阶段：硬限 `10MB`（防 OOM）
- 前端：Base64 编码膨胀 33%

**核心瓶颈**：50MB 文件经 Base64 编码后约 67MB，已超出生产环境 Express 10MB 限制，业务层 50MB 承诺实际无法兑现。

### 2.2 四方案合一改造

| 方案 | 内容 | 实现方式 |
|------|------|----------|
| **A** | 解除 Base64 限制 | 改用 `multer` multipart/form-data 流式上传，单文件上限 200MB |
| **B** | 流式解析 | docParser 上限从 10MB 提升至 50MB，评估 V8 堆内存 |
| **C** | 客户端图片压缩 | 上传前压缩图片型 PDF / 大图，降低体积 |
| **D** | 服务端 ZIP 递归解析 | docParser 增加 `.zip/.rar` 解压分支，内部递归解析每个文件 |

### 2.3 关键改动文件

- `backend/routes/documents.js` — 新增 `/api/documents/upload/multipart` 端点（multer，200MB）
- `backend/services/docParser.js` — 上限提升 + ZIP 递归解析
- `src/components/UploadModal.tsx` — 前端分流：>10MB 走 multipart，≤10MB 走原 base64
- `deploy/nginx-ssl.conf` — `proxy_request_buffering off` 大文件流式上传

### 2.4 验证结果

- 单文件上传上限：50MB → **200MB**（真实可用）
- 设计图纸（100MB+）：支持流式上传与解析
- AI 向量化链路：无需改动，分块处理任意长度文本

## 三、配色方案统一与对比度优化

### 3.1 问题

原配色切换使用图形图标方式（月亮/太阳图标），AI 味儿重，不够正式；且仅能在首页调整，各页面无法随时切换。

### 3.2 改造内容

1. **文字下拉选择样式**：替换图形图标为正式的文字下拉菜单，选项为「亮色 / 暖色 / 暗色」
2. **顶栏集成**：配色选择器放入每个页面的顶栏（ModuleHeader），支持在任意页面随时调整
3. **三套主题对比度校准**：
   - 亮色主题：文字与背景对比度 ≥ 4.5:1（WCAG AA）
   - 暖色主题：用色克制，暖色调背景配深灰文字，避免高饱和暖色导致识别困难
   - 暗色主题：文字亮度适中，避免纯白刺眼

### 3.3 关键改动文件

- `src/components/ModuleHeader.tsx` — 顶栏集成配色下拉选择器
- `src/utils/themeEngine.ts` — 三套主题 CSS 变量对比度校准
- `src/components/GlobalDashboard.tsx` — 移除首页独立配色切换（统一到顶栏）

## 八、开发环境修复

### 8.1 Git SSH 中文路径问题

**问题根因**：
- Git for Windows 自带的 MSYS2 SSH 无法正确处理中文用户名路径（`X1 隐士`）
- 导致 `known_hosts` 和 SSH 密钥无法找到，报 `Host key verification failed` 和 `Permission denied (publickey)`

**解决方案**：
- 设置用户环境变量 `GIT_SSH_COMMAND` 指向系统 OpenSSH：
  ```
  GIT_SSH_COMMAND = C:/Windows/System32/OpenSSH/ssh.exe -o StrictHostKeyChecking=accept-new
  ```
- 系统 OpenSSH（Windows 自带）可以正确处理中文路径
- `-o StrictHostKeyChecking=accept-new` 自动接受新主机密钥
- 新打开的终端自动生效
