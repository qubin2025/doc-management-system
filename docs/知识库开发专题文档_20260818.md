---

## 一、背景与目标

### 1.1 问题
现有知识库仅覆盖"用户上传文档"和"前端 localStorage 业务数据"，后端 SQLite 21 张业务表中的大量数据未纳入向量库与知识图谱，导致项目运行沉淀的核心知识（日报、问题、经验）无法被语义检索与图谱追溯。

### 1.2 目标
将三张高价值业务表自动入库到向量库 + 知识图谱，实现"项目运行沉淀即知识"：
- `daily_reports`（项目日报 8 段模板）
- `mobile_issues`（现场问题）
- `project_experiences`（项目经验库）

---

## 二、现状梳理

### 2.1 知识库两层结构现状

| 层 | 数据源 | 入库机制 | 覆盖度 |
|---|--------|---------|--------|
| 向量库 (IndexedDB + localStorage) | 用户上传文档 | 上传时解析→分块→向量化 | ✓ 仅文档 |
| 知识图谱 (Neo4j + 本地) | localStorage 各键 | `buildGraph()` 重建时同步 | 部分（前端数据） |
| 外部服务 (LightRAG/RAGFlow) | 文档+图谱 | API 调用 | LightRAG 未部署；RAGFlow 浅接入 |

### 2.2 后端三张表入库情况

| 业务表 | 是否入库向量库 | 是否入图谱节点 | 价值评估 |
|---|---|---|---|
| `daily_reports` 日报 8 段模板 | ✗ | ✗ | **高** — 现场第一手资料 |
| `mobile_issues` 现场问题 | ✗ | ✗ | **高** — 风险溯源 |
| `project_experiences` 项目经验库 | ✗ | ✗ | **高** — 知识复用核心 |

### 2.3 已有 API（无需新建读取端点）

| API | 用途 |
|---|---|
| `GET /api/mobile/daily/list?projectName=` | 日报列表 |
| `GET /api/mobile/issue/list?projectName=` | 问题列表 |
| `GET /api/experience/list?category=&keyword=&limit=` | 经验列表 |

## 三、表结构

### 3.1 daily_reports（项目日报 8 段曙光模板）

```sql
CREATE TABLE daily_reports (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id INTEGER NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  report_date TEXT NOT NULL,
  weather_day TEXT, weather_night TEXT, weather_alert TEXT, weather_alert_level TEXT,
  managers_main INTEGER, managers_labor INTEGER, managers_specialty INTEGER,
  workers_main INTEGER, workers_labor INTEGER, workers_specialty INTEGER,
  workers_special INTEGER, workers_total INTEGER,
  machinery TEXT DEFAULT '[]', machinery_total INTEGER,
  materials TEXT DEFAULT '[]',
  tasks TEXT DEFAULT '[]',
  quality_risks TEXT DEFAULT '[]',
  issues TEXT DEFAULT '[]',
  photos TEXT DEFAULT '[]',
  original_text TEXT, notes TEXT,
  reported_by TEXT NOT NULL,
  deleted INTEGER DEFAULT 0,
  created_at TEXT DEFAULT (datetime('now')),
  UNIQUE(project_id, report_date)
);
```

### 3.2 mobile_issues（现场问题）

```sql
CREATE TABLE mobile_issues (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id INTEGER NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  title TEXT NOT NULL,
  description TEXT DEFAULT '',
  severity TEXT DEFAULT 'normal',
  status TEXT DEFAULT 'reported',
  assignee TEXT DEFAULT '',
  photo_path TEXT DEFAULT '',
  reported_by TEXT NOT NULL,
  created_at TEXT, updated_at TEXT
);
```

### 3.3 project_experiences（项目经验库）

```sql
CREATE TABLE project_experiences (
  id TEXT PRIMARY KEY,
  project_name TEXT NOT NULL,
  category TEXT NOT NULL DEFAULT 'general',
  title TEXT NOT NULL,
  description TEXT NOT NULL,
  patterns TEXT DEFAULT '[]',
  metrics TEXT DEFAULT '{}',
  reference_count INTEGER DEFAULT 0,
  created_at TEXT, updated_at TEXT
);
```

## 四、日报 8 段拆块策略

### 4.1 段位定义

| 段号 | 段名 | 来源字段 | 决策 |
|---|---|---|---|
| 1 | 天气 | weather_day/night/alert | 跳过（结构化数据，向量化意义不大） |
| 2 | 人员投入 | managers_*/workers_* | 跳过（结构化数据） |
| 3 | 机械投入 | machinery, machinery_total | 跳过（结构化数据） |
| 4 | 材料进场 | materials | 跳过（结构化数据） |
| 5 | 进度详情 | tasks | **入库**（自然语言价值高） |
| 6 | 质量风险 | quality_risks | **入库**（自然语言价值高） |
| 7 | 现场问题 | issues | **入库**（自然语言价值高） |
| 8 | 原文备注 | original_text + notes | **入库**（截断到 1500 字） |

### 4.2 向量 ID 命名规则

用于去重：日报更新时按 ID 前缀删除旧向量再写新向量。
- 日报：`daily-{reportId}-seg{1-4}`（4 段方案）
- 问题：`issue-{issueId}`
- 经验：`exp-{experienceId}`

### 4.3 文本拼接模板

**段 5 - 进度详情**：
```
【项目日报·进度段】项目: {projectName} 日期: {reportDate}
{tasks 数组每项: 区段={area} 描述={description} 工人={workers} 当日进度={todayPct} 累计进度={totalPct} 进度偏差={scheduleDeviation} 承包商={contractor}}
```

**段 6 - 质量风险**：
```
【项目日报·质量风险段】项目: {projectName} 日期: {reportDate}
{quality_risks 数组每项: 名称={name} 检查情况={inspected} 隐患={hazard}}
```

**段 7 - 现场问题**：
```
【项目日报·现场问题段】项目: {projectName} 日期: {reportDate}
{issues 数组每项: 问题={problem} 原因={cause} 措施={measures} 延误天数={delayDays}}
```

**段 8 - 原文备注**：
```
【项目日报·原文备注段】项目: {projectName} 日期: {reportDate}
{original_text 截断到 1500 字 + notes}
```

### 4.4 问题与经验文本化

**问题文本**：
```
【现场问题】项目: {project_name} 标题: {title}
描述: {description}
严重等级: {severity} 状态: {status} 责任人: {assignee}
报告人: {reported_by} 创建时间: {created_at}
```

**经验文本**：
```
【项目经验】项目: {project_name} 分类: {category}
标题: {title}
描述: {description}
模式: {patterns JSON 序列化}
指标: {metrics JSON 序列化}
引用次数: {reference_count}
```

## 五、容量风险评估

### 5.1 容量计算

单条 768 维向量 ≈ 6.5KB（含 metadata）

| 数据类型 | 单项目/2年容量 | 5 项目 | 10 项目 |
|---|---|---|---|
| 日报（4 段 × 730 天） | 19 MB | 95 MB | 190 MB |
| 问题（365 条） | 2.4 MB | 12 MB | 24 MB |
| 经验（48 条） | 0.3 MB | 1.5 MB | 3 MB |
| **合计** | **21.7 MB** | **108.5 MB** | **217 MB** |

### 5.2 风险点

| 风险 | 等级 | 触发条件 | 影响 |
|---|---|---|---|
| localStorage 单 key 5MB 突破 | 🔴 高 | 单项目 > 800 份日报 | 触发 `clearOldest()`，清空其他项目向量 |
| IndexedDB 200MB 软上限 | 🟡 中 | 5+ 项目 × 2 年数据 | 触发 LRU 淘汰 50 条，丢部分日报段 |
| embedText API 速率 | 🟡 中 | 单次全量同步 5000+ 调用 | 单条 1s，5000 条需 80 分钟 |

### 5.3 缓解措施（已确认执行）

1. **日报精简入库**：仅入库 4 段（进度/质量风险/现场问题/原文备注），跳过天气/人员/机械/材料结构化数据
2. **localStorage 容量预警**：写入前检测项目向量大小 > 4MB 时，**只写 IndexedDB** 跳过 localStorage（避免 `clearOldest` 误删其他项目）
3. **增量同步**：按 `updated_at > since` 过滤，避免重复入库
4. **去重写入**：日报/问题/经验更新时，按 ID 前缀删除旧向量再写入
5. **批量同步节流**：每条 embedText 间隔 200ms，避免后端 embedding 服务过载

## 八、风险与回滚

- 全程不破坏现有 `vectorStore` 接口（仅新增方法）
- 同步失败有 toast 提示，不影响现有文档检索
- 出现严重问题时可禁用"同步业务数据"按钮，老向量库继续工作

### 回滚策略

```bash
# 禁用同步功能（无需删数据）
# 在 KnowledgeBase.tsx 注释 "同步业务数据" 按钮即可

# 清理已入库的业务数据向量
# 在浏览器控制台执行：
vectorStore.getAllDocs().filter(d => d.id.startsWith('daily-') || d.id.startsWith('issue-') || d.id.startsWith('exp-')).forEach(d => vectorStore.remove(d.id))
```
